Every token has an address

Clang encodes a source location as one 32-bit integer, an offset into a single address space. Every file the compiler enters is given a contiguous range in it, sized by the file.

the source-location address space

Diagnostics, fix-its, debug info: everything that names a line resolves through this space. It stays fast because a location is just a number.

And it is finite. About 2 GB of addresses for every character of source the compilation ever sees.

Two modules, one header

The whole talk starts from this shape: two modules, built separately, each one textually including the same header.

module A
#include "shared.h"
int a_fn();
module B
#include "shared.h"
int b_fn();
shared.h, 4,890 B

Each module is a separate compiler invocation writing its own self-contained PCM. So each one enters shared.h itself, and serializes its own record of everything it saw.

Modules multiply the same file

One space serves the whole compilation. The current TU grows from the bottom; everything loaded from PCMs is carved from the top, down.

Alone, a TU barely dents the space: include guards enter a shared header once, and few TUs hold two billion characters.

But each PCM is self-contained, so each serialized its own entries for every header it included textually. Load N modules, and the same header is live N times at once.

fatal error: ran out of source locations

Reports of exactly this kept arriving from large module builds. The space runs out and the build stops.

First idea: fix it when loading

The duplicates meet each other at load time. So catch them there: deduplicate on the reader side.

  • While loading module B, notice that shared.h was already loaded from module A.
  • Give B’s copy no new range; resolve its locations against A’s copy instead.
  • The address space only ever holds one copy per file.

Easy to say. The hard part is what the files on disk already assume.

B’s copy is collapsed onto A’s, so every location that pointed into it must be rewritten…

…and everything after it shifts back. A forward map translates disk → memory, an inverse map must undo it when a module is re-serialized.

The inverse of a piecewise map is not one subtraction. Getting that wrong corrupted locations on ROOT, found the hard way.

The cost: nothing stays lazy

To compact the space before allocating it, the loader must read every location entry of every loaded module, up front.

Clang’s designan entry is materialized only when something touches it
Reader-side dedupall of them, for all modules, at startup

The eager scan showed up exactly where you’d expect: slower interpreter startup and higher peak memory on ROOT, regressing the fundamentals the patch has no business touching.

Saved the space, lost the fundamentals.

Keep the goal, change the place.

Prevent, don’t repair

mod1.h
shared.h entries
B.pcm
mod2.h
shared.h entries

Two files on disk, carrying identical entries for the same header.

Clang already does something close to this: when writing a PCM, it drops module-map files that don’t affect the build. That machinery came out of builds that were hitting exactly this problem.

A module map is the file that declares which headers form a module. When one is dropped, its locations are simply never written.

Nothing written  ⇒  nothing to remap later.

So generalize it: extend the same machinery from module maps to the headers themselves. Move deduplication to the writer, and make sure the second copy never exists.

  • While writing B: does a module I import already provide this file?
  • Yes → write no location entries for it. Encode its locations against A.
  • Loading B allocates nothing for shared.h. No remapping, no inverse map, nothing eager.

Serialized locations were already {module-file, offset} pairs (0 = “this module”). The patch just lets that pair point at the module that owns the entries. The reader resolves it directly. No translation table, no fixup pass.

Finding A’s copy without scanning

  • Who has this file? Candidates bucketed by size, filtered by file name, confirmed by real path. The key only narrows the search; the path check decides.
  • Where exactly is their copy? That used to need a scan of A’s entries. Now INPUT_FILE records it directly:
INPUT_FILE {
  path: "shared.h", size: 4890, …  // already there
  sloc_index: 6,  sloc_offset: 1000  // new
}
  • index, which entry in A’s table it is: names the file without searching for it.
  • offset, where its range starts: the number the subtraction on the last slide needs.

Two integers per input file, a few bytes each, and the per-module scan they replaced was deleted outright.

A decision: eager map or lazy table

The lookup map is built once over the loaded modules, work proportional to the imports. The alternative raised in review: serialize a query table into every PCM, like HeaderFileInfo, work proportional to the module being written.

  • The table costs ~2 KB per PCM, written into every module, including leaves nobody ever queries. Those are exactly the bytes SDK vendors guard.
  • After keying by size and filtering by name, the eager build is cheap at every scale we could measure.
  • Verdict: not worth it yet. Revisit it if a workload ever shows the walk dominating.

The scan cost is small, understood to the instruction, and paid only where the feature actually fires.

Apple’s SDKs are modularized bottom-up, so they have little duplication left to reclaim. The savings show up where duplication actually exists, and nothing regresses where it doesn’t.

One copy is enough

ProblemEvery module carries its own copy of shared headers; the 32-bit source-location space runs out, and builds crash.
ApproachNever write the second copy. When writing a module, redirect a shared file’s locations to the module that already provides it.
Result−19% loaded location space on ROOT; compile time and memory stable; one small, measured scanning cost.
